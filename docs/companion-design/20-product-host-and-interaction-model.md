# 20 — 产品宿主与交互模型

## 目标

为咪兔建立一份明确的产品宿主与交互模型总纲，统一回答:

1. 咪兔运行在什么产品载体里
2. “终端风格”到底指什么，不指什么
3. 用户通过哪些入口与咪兔互动
4. 前端、后端、协议、存储分别承担什么角色

这份文档的作用，是作为 15-19 号玩法文档之上的总纲约束，防止后续设计和实现重新滑回
"真实终端应用"的错误前提。

## 核心结论

咪兔是一个**运行在网页版 / App 中的 companion 模块**。

它不是:

- 系统 shell 中运行的 TUI 宠物
- 依赖用户在真实命令行输入指令的应用
- 只能存在于某个终端窗口中的小组件

它是:

- 一个以终端风格呈现的网页 / App companion
- 一个嵌在聊天、工作、登录、陪伴面板中的产品能力
- 一个以低干扰、黑白点线、ASCII 美学呈现的长期养成角色

## 一句话定义

```text
咪兔 = 网页 / App 宿主中的终端风格 companion，
      而不是终端宿主中的 companion。
```

## 设计原则

| 原则 | 说明 |
|------|------|
| 宿主先行 | 先明确它是网页 / App 模块，再定义风格和交互 |
| 风格与载体分离 | 终端风是表现语言，不是运行环境 |
| 交互入口可多态 | 同一动作可来自按钮、快捷入口、slash palette、悬浮菜单 |
| 规则只在后端 | 产品入口多样，但业务判断仍由 backend 决定 |
| 前端只负责体验映射 | 把状态映射成界面、动画、面板，不创造业务真相 |
| 同一模型跨端复用 | Web 与 App 共享宿主模型、协议模型、状态模型 |

## 一、产品宿主定义

## 1.1 宿主形态

咪兔可出现在以下宿主场景中:

| 宿主场景 | 定位 | 优先级 |
|---------|------|:--:|
| 登录页 | 第一眼吸引、建立独特性 | 高 |
| 聊天 / 工作主页面 | 长期陪伴、轻反馈、主交互 | 最高 |
| Header / 悬浮入口 | 快速打开状态与面板 | 高 |
| Companion 专属面板 | 养成、回忆、收藏、目标 | 高 |
| 小游戏容器 | 调味互动，不是主宿主 | 中 |

## 1.2 宿主不是终端

为了避免歧义，这里明确禁止以下理解:

- 把页面输入框当成系统命令行
- 把 companion 入口当成必须输入命令才能使用的能力
- 把窄屏适配理解成 shell 列宽适配

这里允许的终端风含义只有:

- ASCII / 点线 /黑白界面
- 类命令面板与快捷入口
- 开发者工具氛围
- 简洁、低干扰、信息密度克制的交互结构

## 二、终端风格落点

终端风格不是一个单点设计，而是四层共同决定的。

## 2.1 视觉层

包括:

- ASCII 精灵
- 点阵状态条
- 黑白 / 低饱和
- 线框边界
- 稀有星点 / 呼吸点

## 2.2 布局层

包括:

- 小面板
- 低打扰浮层
- 边角 companion 区
- 极简信息模块

## 2.3 交互层

包括:

- 快捷入口
- slash palette
- 悬浮操作
- 一步完成的小交互

## 2.4 气质层

包括:

- 开发者工作流陪伴感
- 像工具又不只是工具
- 极简但不冷
- 安静但有性格

## 三、交互入口模型

咪兔的交互模型必须“动作统一、入口多态”。

这意味着:

- 业务动作只有一套
- 触发入口可以有多种

## 3.1 标准动作集合

这是产品级动作，不是实现级命令。

| 动作 ID | 含义 | 对应体验 |
|--------|------|---------|
| `buddy.open` | 打开总览面板 | 看它现在怎么样 |
| `pet.trigger` | 摸头 / 安抚 | 轻情感互动 |
| `feed.open` | 打开喂食入口 | 照顾行为 |
| `play.open` | 打开互动玩法入口 | 调味玩法 |
| `goal.open` | 打开目标面板 | 查看今天和这周 |
| `memory.open` | 打开回忆面板 | 回看共同历史 |
| `collection.open` | 打开收藏面板 | 查看房间 / 穿戴 / 图鉴 |

## 3.2 入口映射

同一个动作可以从多个 UI 入口触发。

| 动作 | 可用入口 |
|------|---------|
| `buddy.open` | Header 按钮、悬浮球、slash palette、精灵点击 |
| `pet.trigger` | 精灵点击、长按、快捷按钮、面板内按钮 |
| `feed.open` | 面板按钮、快捷按钮、slash palette |
| `goal.open` | Header 小红点、面板标签、快捷入口 |
| `memory.open` | 面板标签、周总结 CTA、收藏页入口 |

### 约束

- 文档定义动作，不绑定唯一入口
- UI 可以调整入口样式，但不能改动作语义

## 3.3 slash palette 的地位

slash palette 可以存在，但它是**一种入口实现**，不是系统的唯一交互方式。

正确关系:

```text
slash palette -> 触发产品动作
按钮 / 点击 / 浮层 -> 触发同一个产品动作
```

错误关系:

```text
只有输入 /buddy 才能打开 companion
```

## 四、界面分层模型

咪兔在产品里分为三层界面，这与 [17-terminal-ui-ux.md](file:///Users/yuanbaishu/pythonProject/agent-core/docs/companion-design/17-terminal-ui-ux.md) 一致，但本节定义的是“宿主关系”。

## 4.1 常驻层

定位:

- 让用户知道它一直在
- 尽量不抢主任务

常见宿主位置:

- 聊天页一角
- 页面底部悬浮区
- Header 关联区

## 4.2 轻展开层

定位:

- 1-5 秒内完成一次轻交互
- 不把用户带离主工作流

常见内容:

- `buddy`
- `goal`
- `feed`
- `play`

## 4.3 深信息层

定位:

- 让长期养成有沉淀可回看
- 适合收藏和回忆，不适合高频打开

常见内容:

- `memory`
- `album`
- `collection`
- `stats`

## 五、页面生命周期模型

咪兔不是永远全功能在线，而是跟随页面宿主存在不同生命周期。

## 5.1 登录页

目标:

- 视觉 hook
- 稀有度揭示
- 建立“独一无二”的第一印象

特征:

- 弱交互
- 强视觉
- 少系统信息

## 5.2 工作页 / 聊天页

目标:

- 长期陪伴
- 事件反馈
- 低打扰互动

特征:

- 常驻层最重要
- 轻展开层高频
- 深信息层低频

## 5.3 Companion 面板

目标:

- 承载养成深度
- 展示目标、回忆、收藏

特征:

- 信息更多
- 仍保持终端风极简布局

## 六、前后端职责映射

为了保证隔离性，这份宿主模型必须与 [14-frontend-backend-boundary.md](file:///Users/yuanbaishu/pythonProject/agent-core/docs/companion-design/14-frontend-backend-boundary.md) 和 [appendix/sse-schema.md](file:///Users/yuanbaishu/pythonProject/agent-core/docs/companion-design/appendix/sse-schema.md) 对齐。

## 6.1 Backend 负责

- 决定情绪
- 决定奖励
- 决定目标
- 决定回忆
- 决定收藏解锁
- 决定文本内容

## 6.2 Frontend 负责

- 把动作映射到 UI 入口
- 把状态映射到终端风界面
- 管理浮层、面板、动画与降级
- 管理 Web / App 宿主差异

## 6.3 Frontend 明确禁止

- 因按钮位置不同而定义不同业务逻辑
- 根据点击位置推导 bond / mood
- 在本地构造 companion 业务真相

## 七、跨端一致性模型

Web 和 App 可以长得略有不同，但必须共享同一套动作语义和状态结构。

## 7.1 必须一致

- 业务动作 ID
- SSE 事件协议
- 面板数据结构
- 资源含义
- 回忆 / 收藏语义

## 7.2 可以不同

- 面板展开方式
- 动画细节
- 悬浮位置
- 手势与 hover 行为
- App 专属轻震动 / Web 专属 hover 提示

## 八、可扩展性规则

为了后续扩展新玩法、新面板、新入口，不破坏整体模型，必须遵循以下规则。

## 8.1 新功能优先新增动作，不直接新增特殊入口

正确:

```text
新增 action: diary.open
然后 Web / App 分别决定入口
```

错误:

```text
先在 App 右下角加一个私有按钮，
没有统一动作定义
```

## 8.2 新入口必须映射到既有动作或显式新增动作

任何新按钮、浮层、快捷方式，都必须能追溯到:

- 已有动作
- 或新增的动作定义

## 8.3 新面板必须说明属于哪一层

每个新面板都要先回答:

- 它是常驻层、轻展开层还是深信息层？
- 如果是深信息层，为什么值得存在？

## 8.4 新宿主场景必须回答这三件事

如果未来要把咪兔扩展到新页面，比如通知中心或个人主页，必须先说明:

1. 为什么它应该出现在这里
2. 它在这里承担什么体验目标
3. 它在这里不该做什么

| 推荐术语 | 含义 |
|---------|------|
| `终端风格` | 视觉与交互语言 |

## 最终体验

用户不该觉得自己在使用一个“伪装成网页的终端工具”。

用户应该觉得:

- 这是一个网页 / App 产品
- 但它有非常独特的终端风格气质
- 咪兔一直住在这个产品世界里
- 自己和它的互动自然、轻巧、低打扰，又能慢慢积累出关系

这份文档的作用，就是确保后续所有设计和实现都站在这个正确前提上。
