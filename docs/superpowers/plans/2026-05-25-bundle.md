## 1. 概述

### 1.1 什么是 Bundle

Bundle（技能包）是一个 **YAML 别名文件**，它将多个独立技能（skill）绑定到一个斜杠命令下。用户输入 `/backend-dev`，等同于同时激活 `github-code-review`、`test-driven-development`、`github-pr-workflow` 三个技能。

### 1.2 解决的问题

| 场景 | 无 Bundle | 有 Bundle |
|------|----------|----------|
| 开始一个后端特性开发 | 依次输入 `/github-code-review`、`/test-driven-development`、`/github-pr-workflow` | 输入 `/backend-dev` 一次 |
| 每次重复相同技能组合 | 每次都手动逐个调用 | 定义一次 bundle，永久复用 |
| 团队成员共享工作流 | 口头/文档约定要加载哪些技能 | 提交 bundle 文件到共享目录 |

### 1.3 与单个技能的关系

```
单个技能 (Skill)              技能包 (Bundle)
─────────────                ────────────────
SKILL.md 文件                YAML 文件（仅声明引用关系）
定义"怎么做"                  定义"用哪些技能一起做"
LLM 执行指令                  LLM 同时看到多条指令
```

Bundle **不重复定义技能内容**，只声明引用。技能内容仍从原始 `SKILL.md` 文件加载。

## 2. 核心设计理念

### 2.1 LLM 即编排者

**Bundle 不做工作流编排。** 它把所有技能指令一次性注入 LLM 上下文窗口，由模型自己阅读、理解并决定何时应用哪个技能。这意味着：

- 没有 DAG、状态机或步骤定义
- 技能之间没有显式的执行顺序或数据依赖
- LLM 的推理能力替代了传统的 workflow engine

### 2.2 技能内容 = 提示词

每个技能的 `SKILL.md` 内容本质上是写给 LLM 的指令文本。Bundle 将它们拼接在一起（加标头区分），LLM 将其视为"当前回合的活跃指导"。

### 2.3 宽恕性设计

Bundle 引用的技能如果用户未安装，**不会报错阻断**——只是跳过并在消息中注明。这使得 bundle 可以跨环境共享，即使不同开发者的技能库不完全一致。

## 3. 数据模型

### 3.1 YAML 文件格式

```yaml
# ~/.hermes/skill-bundles/backend-dev.yaml
name: backend-dev
description: 后端特性开发 — 代码评审、TDD 开发、PR 工作流
skills:
  - github-code-review
  - test-driven-development
  - github-pr-workflow
instruction: |
  可选的附加指导，注入到所有技能内容之上。
  当技能之间有冲突时，优先遵循 TDD 的流程。
```

### 3.2 字段规约

| 字段 | 必填 | 类型 | 说明 |
|------|------|------|------|
| `name` | 否* | string | 展示名称，缺省使用文件名（不含扩展名） |
| `description` | 否 | string | 描述文本，在 `/help` 和 `hermes bundles list` 中展示 |
| `skills` | **是** | string[] | 引用的技能名称列表，至少一个 |
| `instruction` | 否 | string | 注入到技能内容之上的附加指导 |

> *name 缺省时，取文件名的 stem（如 `backend-dev.yaml` → `backend-dev`）

### 3.3 内存中的数据结构

```python
{
    "/backend-dev": {
        "name": "backend-dev",
        "slug": "backend-dev",
        "description": "后端特性开发 — 代码评审、TDD 开发、PR 工作流",
        "skills": ["github-code-review", "test-driven-development", "github-pr-workflow"],
        "instruction": "当技能之间有冲突时，优先遵循 TDD 的流程。",
        "path": "/Users/xxx/.hermes/skill-bundles/backend-dev.yaml"
    }
}
```

使用 `/{slug}` 作为 key 的 dict，与技能命令注册表 `{"/skill-name": skill_info}` 保持相同的数据结构约定。

## 4. 存储策略

### 4.1 文件系统布局

```
~/.hermes/
├── skill-bundles/          # bundle 目录
│   ├── backend-dev.yaml
│   ├── research.yaml
│   └── deploy.yaml
├── skills/                 # 技能目录（独立）
│   ├── github-code-review/
│   │   └── SKILL.md
│   ├── test-driven-development/
│   │   └── SKILL.md
│   └── ...
└── config.yaml
```

### 4.2 设计要点

- **一个文件一个 bundle**：方便文件级 CRUD、版本控制、团队共享
- **与技能目录分离**：bundle 不修改技能文件，技能不知道自己被哪些 bundle 引用
- **支持 yaml/yml 两种扩展名**：降低用户使用摩擦
- **目录不存在时优雅降级**：返回空列表，不报错

### 4.3 环境变量覆盖

```python
# 测试或特殊部署场景下，可用环境变量覆盖 bundle 目录
HERMES_BUNDLES_DIR=/custom/path
```

## 5. 名称规范化

### 5.1 Slug 算法

```python
def _slugify(name: str) -> str:
    cmd = name.lower().replace(" ", "-").replace("_", "-")
    cmd = re.sub(r"[^a-z0-9-]", "", cmd)      # 移除非字母数字和连字符
    cmd = re.sub(r"-{2,}", "-", cmd).strip("-") # 合并多余连字符
    return cmd
```

| 输入 | 输出 |
|------|------|
| `Backend Dev` | `backend-dev` |
| `My_Super_Skill` | `my-super-skill` |
| `Foo++Bar` | `foo-bar` |
| `---test---` | `test` |

### 5.2 为什么重要

- 斜杠命令作为 dict key 查找，必须确定性地匹配
- Telegram 等平台将连字符转换为下划线，规范化后的一致性保证跨平台命令互通
- bundle 和 skill 使用**相同的 slug 算法**，确保冲突检测正确

## 6. 缓存与懒加载

### 6.1 缓存架构

```
┌─────────────────────────────────────────┐
│              get_skill_bundles()          │
│                                          │
│  ┌──────────────────────────────────┐   │
│  │  检查 mtime: 目录 + 所有文件      │   │
│  │  if mtime == _bundles_cache_mtime │   │
│  │    → 返回缓存 (零 IO)             │   │
│  │  else                             │   │
│  │    → scan_bundles() 重建缓存       │   │
│  └──────────────────────────────────┘   │
│                                          │
│  _bundles_cache: Dict[str, Dict]         │
│  _bundles_cache_mtime: float             │
└─────────────────────────────────────────┘
```

### 6.2 mtime 检测细节

```python
def _max_mtime(files: list[Path]) -> float:
    """取目录 mtime 和所有文件 mtime 中的最大值。

    目录 mtime 检测文件删除，文件 mtime 检测内容修改。
    两者结合是一个廉价的"是否变更"检测。
    """
    mtimes = [base.stat().st_mtime for base in [bundles_dir()]]
    for f in files:
        mtimes.append(f.stat().st_mtime)
    return max(mtimes)
```

### 6.3 为什么用 mtime 而不是 inotify/watchdog

- **零依赖**：不需要文件系统监控库
- **足够准确**：bundle 变更频率极低（用户手动创建/编辑），mtime 粒度完全够用
- **懒检测**：只在下次调用 `get_skill_bundles()` 时才检查，不会在后台消耗资源
- **开销极低**：`stat()` 系统调用是 O(1) 操作

## 7. 调度流程

### 7.1 CLI 调度

```
用户输入: /backend-dev fix the login bug
                │
                ▼
    ┌──────────────────────┐
    │ 1. 解析斜杠命令       │
    │    base_cmd = "/backend-dev"
    │    user_instruction = "fix the login bug"
    └──────┬───────────────┘
           │
           ▼
    ┌──────────────────────┐
    │ 2. Bundle 优先检查    │
    │    base_cmd in skill_bundles?
    │    YES → 进入 bundle 分支
    └──────┬───────────────┘
           │
           ▼
    ┌──────────────────────┐
    │ 3. 构建调用消息       │
    │    build_bundle_invocation_message(
    │        cmd_key="/backend-dev",
    │        user_instruction="fix the login bug"
    │    )
    └──────┬───────────────┘
           │
           ▼
    ┌──────────────────────┐
    │ 4. 逐个加载技能       │
    │    for skill in skills:
    │        _load_skill_payload(skill)
    │        → SKILL.md 内容
    │        → 预处理（模板变量、shell 展开）
    │        → _build_skill_message()
    └──────┬───────────────┘
           │
           ▼
    ┌──────────────────────┐
    │ 5. 拼接完整消息       │
    │    [HEADER: bundle 信息]
    │    [SKILL 1 内容]
    │    [SKILL 2 内容]
    │    [SKILL 3 内容]
    └──────┬───────────────┘
           │
           ▼
    ┌──────────────────────┐
    │ 6. 注入 agent 输入    │
    │    self._pending_input.put(msg)
    │    → 作为用户消息发送给 LLM
    └──────────────────────┘
```

### 7.2 Gateway（多平台）调度

Gateway 的流程与 CLI 几乎一致，代码在 `gateway/run.py:7593-7619`：

```python
# Bundle 优先于单个技能

bundle_key = resolve_bundle_command_key(command)
if bundle_key is not None:
    bundle_result = build_bundle_invocation_message(
        bundle_key, user_instruction, task_id=task_id
    )

        msg, _loaded, missing = bundle_result
        event.text = msg          # 替换事件文本为 bundle 的全部内容
        _bundle_handled = True
        # 继续走正常消息处理流程

# 如果不是 bundle，再尝试单个技能

    cmd_key = resolve_skill_command_key(command)
    if cmd_key is not None:
        # ... 加载单个技能
```

### 7.3 调度优先级

```
斜杠命令输入
    │
    ├─ 1. 内置命令 (/help, /clear, /exit ...)
    ├─ 2. Plugin 注册的命令
    ├─ 3. Bundle ★ (优先于同名技能)
    ├─ 4. 单个技能
    └─ 5. 前缀模糊匹配回退
```

```
  review_level = thorough
]

────────────────────────────────────────────────────

[Loaded as part of the "backend-dev" skill bundle.]

# Test-Driven Development

... 完整 SKILL.md 内容 ...

[Skill directory: /Users/xxx/.hermes/skills/test-driven-development]

────────────────────────────────────────────────────

[Loaded as part of the "backend-dev" skill bundle.]

# GitHub PR Workflow

... 完整 SKILL.md 内容 ...

[Skill directory: /Users/xxx/.hermes/skills/github-pr-workflow]
```

### 8.3 消息构造的步骤

1. **查 bundle**：从缓存获取 bundle 信息
2. **遍历技能列表**：对每个 `skill_id`
   - 调用 `_load_skill_payload(skill_id)` 加载技能（复用单个技能的加载逻辑）
   - 已处理的跳过（`seen` set 去重）
   - 不存在的记入 `missing` 列表，不阻断
   - 调用 `_build_skill_message()` 格式化单个技能
3. **构建 Header**：bundle 名称、已加载技能列表、缺失技能列表、附加指导、用户指令
4. **拼接返回**：`header + 空行 + skill_blocks`

### 8.4 技能消息的预处理

每个技能在加载时经过 `_build_skill_message()`（`agent/skill_commands.py:160`）：

| 处理步骤 | 说明 |
|---------|------|
| 模板变量替换 | `{{ variable }}` → config.yaml 中的值 |
| 内联 Shell 展开 | `$(command)` → 命令输出（可配置开关） |
| 技能目录注入 | 告知 LLM 技能文件的绝对路径，方便引用脚本 |
| 配置变量注入 | 从 config.yaml 读取技能声明的配置值 |
| 支持文件列表 | 列举 `references/`、`scripts/`、`templates/` 下的文件 |

## 9. 冲突解决

### 9.1 Bundle vs 技能同名

**Bundle 胜出。** 这是有意为之的设计：

```python
# cli.py 中的调度顺序
elif base_cmd in skill_bundles:      # ← 先检查 bundle
    ...
elif base_cmd in skill_commands:     # ← 后检查技能
    ...
```

理由：用户显式命名了一个 bundle `research`，意味着他想要 `/research` 指向 bundle 而非同名的独立技能。

### 9.2 重复 Slug 的 Bundle

如果两个 bundle 文件产生相同的 slug（如 `Backend-Dev.yaml` 和 `backend_dev.yaml`），**第一个（按字母序）胜出**，后续的打印 warning 跳过。

### 9.3 去重

同一个技能在 bundle 的 `skills` 列表中重复出现时，只加载一次（`seen` set 控制）。

| **List** | `list_bundles()` | 返回排序后的 bundle 列表 |
| **Reload** | `reload_bundles()` | 强制重新扫描，返回 diff（added/removed/unchanged） |

### 10.2 交互式创建（CLI）

```bash
hermes bundles create my-workflow --skill skill-a --skill skill-b
# 如果不传 --skill，进入交互模式：
#   skill> skill-a
#   skill> skill-b
#   skill>        # 空行结束
```

### 10.3 变更检测与热加载

```
定时器/事件循环中每次可能用到 bundle 时
    └─ get_skill_bundles()
         └─ 比较当前 mtime 与缓存 mtime
              ├─ 相同 → 返回缓存 (无 IO)
              └─ 不同 → scan_bundles() 重建
```

没有显式的 "watch" 线程，借每次调用做懒检测。对于 bundle 这种低频变更的场景完全够用。

## 11. 复现指南

### 11.1 最小化复现步骤

如果你的 agent 服务已有技能系统（类似 Hermes 的 `SKILL.md` 文件），按以下步骤加入 bundle 能力：

#### Step 1: 定义 Bundle 数据模型

```python
# bundle 的 YAML 格式
BUNDLE_SCHEMA = """
name: str          # bundle 名称
description: str   # 可选描述
skills:            # 必填，技能名称列表
  - skill-a
  - skill-b
instruction: str   # 可选，附加指导
"""
```

#### Step 2: 实现文件扫描与缓存

```python
import os
import yaml
from pathlib import Path

class BundleRegistry:
    def __init__(self, bundles_dir: Path):
        self._dir = bundles_dir
        self._cache: dict[str, dict] = {}
        self._mtime: float = 0.0

    def _max_mtime(self) -> float:
        if not self._dir.exists():
            return 0.0
        mtimes = [self._dir.stat().st_mtime]
        for f in self._dir.glob("*.yaml"):
            mtimes.append(f.stat().st_mtime)
        for f in self._dir.glob("*.yml"):
            mtimes.append(f.stat().st_mtime)
        return max(mtimes)

    def _slugify(self, name: str) -> str:
        import re
        cmd = name.lower().replace(" ", "-").replace("_", "-")
        cmd = re.sub(r"[^a-z0-9-]", "", cmd)
        cmd = re.sub(r"-{2,}", "-", cmd).strip("-")
        return cmd

    def _load_file(self, path: Path) -> dict | None:
        try:
            data = yaml.safe_load(path.read_text(encoding="utf-8"))
        except Exception:
            return None
        if not isinstance(data, dict):
            return None

        name = str(data.get("name") or path.stem).strip()
        skills = data.get("skills") or []
        if not isinstance(skills, list) or not skills:
            return None

        slug = self._slugify(name)
        return {
            "name": name,
            "slug": slug,
            "description": str(data.get("description") or "").strip(),
            "skills": [str(s).strip() for s in skills if str(s).strip()],
            "instruction": str(data.get("instruction") or "").strip(),
            "path": str(path),
        }

    def scan(self) -> dict[str, dict]:
        if not self._dir.exists():
            self._cache = {}
            return {}

        out: dict[str, dict] = {}
        for f in sorted(self._dir.glob("*.yaml")):
            info = self._load_file(f)
            if info:
                key = f"/{info['slug']}"
                if key not in out:
                    out[key] = info
        self._cache = out
        self._mtime = self._max_mtime()
        return out

    def get_all(self) -> dict[str, dict]:
        if self._max_mtime() != self._mtime:
            self.scan()
        return self._cache

    def resolve(self, command: str) -> str | None:
        """将用户输入的命令映射为 bundle key"""
        if not command:
            return None
        key = f"/{command.replace('_', '-')}"
        return key if key in self.get_all() else None
```

#### Step 3: 实现消息构造

```python
def build_bundle_message(
    registry: BundleRegistry,
    skill_loader,        # 你的技能加载函数
    cmd_key: str,
    user_instruction: str = "",
) -> tuple[str, list[str], list[str]] | None:
    """构造 bundle 的完整调用消息"""
    info = registry.get_all().get(cmd_key)
    if not info:
        return None

    loaded_names: list[str] = []
    missing: list[str] = []
    skill_blocks: list[str] = []
    seen: set[str] = set()

    for skill_id in info["skills"]:
        identifier = skill_id.strip()
        if not identifier or identifier in seen:
            continue
        seen.add(identifier)

        content = skill_loader(identifier)
        if content is None:
            missing.append(identifier)
            continue

        activation = f'[Loaded as part of the "{info["name"]}" skill bundle.]'
        skill_blocks.append(f"{activation}\n\n{content}")
        loaded_names.append(identifier)

    if not skill_blocks:
        return None

    header = (
        f'[IMPORTANT: The user has invoked the "{info["name"]}" skill bundle, '
        f"loading {len(loaded_names)} skills together. Treat every skill below "
        "as active guidance for this turn.]\n\n"
        f"Bundle: {info['name']}\n"
        f"Skills loaded: {', '.join(loaded_names)}"
    )
    if missing:
        header += f"\nSkills missing (skipped): {', '.join(missing)}"
    if info.get("instruction"):
        header += f"\n\nBundle instruction: {info['instruction']}"
    if user_instruction:
        header += f"\n\nUser instruction: {user_instruction}"

    return ("\n\n".join([header] + skill_blocks), loaded_names, missing)
```

```python
    if bundle_key is not None:
        msg, loaded, missing = build_bundle_message(
            bundle_registry, load_skill, bundle_key, user_input
        )
        if msg:
            return send_to_llm(msg)

    # 3. 单个技能
    skill_key = skill_registry.resolve(command)
    if skill_key is not None:
        return send_to_llm(load_skill(skill_key))

    # 4. 未找到
    return f"Unknown command: /{command}"
```

### 11.2 不依赖 Hermes 内部实现的独立实现

如果你的 agent 服务没有 Hermes 的技能系统，需要实现的核心模块：

| 模块 | 职责 | 复杂度 |
|------|------|--------|
| **Bundle 文件解析** | 读 YAML，校验字段 | 低 |
| **名称规范化** | slug 算法，统一 key 格式 | 低 |
| **mtime 缓存** | 懒检测文件变更 | 低 |
| **消息构造** | 拼接多个技能内容 | 中 |
| **技能加载** | 读取技能文件，模板变量替换 | 中 |
| **调度集成** | 在斜杠命令 dispatch 中插入 bundle 分支 | 低 |

### 11.3 与现有系统的集成模式

#### 模式 A: 同名函数替换（最简单）

如果你的 `/skill-name` 调度入口是 `handle_skill_command(name, args)`：

1. 在 `handle_skill_command` 调用前插入 `handle_bundle_command(name, args)`
2. `handle_bundle_command` 查 bundle 表，命中则展开为多条技能内容注入 LLM
3. 不命中则回退到原有逻辑

#### 模式 B: 中间件/插件

如果你的系统有中间件机制：

```python
class BundleMiddleware:
    def on_slash_command(self, command, args, next_handler):
        bundle = self.registry.resolve(command)
        if bundle:
            return self.expand_and_inject(bundle, args)
        return next_handler(command, args)
```

#### 模式 C: LLM 工具调用

如果你的 agent 使用 function calling：

```python
# 将 bundle 暴露为 LLM 可调用的函数
@tool
def activate_bundle(name: str) -> str:
    """激活一个技能包，加载其中所有技能的完整指令"""
    bundle = registry.get(name)
    if not bundle:
        return f"Bundle '{name}' not found."
    return build_bundle_message(bundle)
```

### 11.4 注意事项

1. **上下文窗口消耗**：Bundle 将所有技能内容全部加载到当前上下文。如果单个技能内容很大（如 5000 token），3 个技能的 bundle 就是 15000 token。需要在 bundle 创建时提醒用户，或限制单个 bundle 的技能数量。

2. **技能冲突处理**：多个技能可能给出矛盾指令。当前方案依赖 LLM 自行判断优先级。如需更精确控制，可利用 `instruction` 字段写入冲突解决规则。

3. **嵌套引用**：Hermes 不支持 bundle 引用 bundle（没有递归展开）。如果需要分层复用，在其上叠加 kanban swarm 而非嵌套 bundle。

4. **热加载时机**：mtime 检测在每次 `get_all()` 时发生。对于高频调用的系统，考虑加 debounce（如至少间隔 5 秒才重新 stat）。

5. **序列化格式**：使用 `yaml.safe_load` 而非 `yaml.load`，防止任意代码执行。

## 12. 关键设计决策与权衡

| 决策 | 选择 | 理由 | 代价 |
|------|------|------|------|
| 编排方式 | LLM 自主阅读多条技能指令 | 零工程复杂度，灵活适应各种技能组合 | 依赖模型能力，无法保证执行顺序 |
| 存储格式 | YAML 文件 | 人类可读写，易于版本控制，无数据库依赖 | 并发写入不安全（但实际场景几乎不会并发写） |
| 缓存策略 | mtime 懒检测 | 零依赖，极低开销 | 不实时（NFS 等场景可能不准确） |
| 冲突处理 | Bundle 优先于同名技能 | 用户显式创建 bundle 就是想要它 | 可能意外覆盖用户想用的独立技能 |
| 缺失技能 | 跳过并继续 | 跨环境兼容，不会因缺少一个技能而阻断 | 加载的技能可能不完整 |
| 变更检测粒度 | 整个目录的 max mtime | 一次 stat 判断是否需要重新扫描 | 任何 bundle 修改都导致全量重新扫描 |
| 命名规则 | 统一的 slug 算法 | 跨平台（CLI/Telegram/Discord）命令一致 | 丢失原始大小写和特殊字符信息 |

## 附录 B: 测试要点

在目标系统上复现后，建议覆盖以下测试场景：

1. **基本功能**：创建 bundle → `/bundle-name` → LLM 收到所有技能内容
2. **缺失技能**：bundle 引用不存在的技能 → 跳过并提示，不阻断
3. **名称冲突**：bundle 和技能同名 → bundle 优先
4. **缓存刷新**：修改 YAML 文件 → 下次调用自动加载新内容
5. **热加载**：删除 bundle 文件 → reload 后 diff 反映删除

7. **重复技能**：同一技能在列表中重复 → 去重，只加载一次
8. **用户指令传递**：`/bundle 附加指令` → 附加指令出现在消息中
9. **模板变量**：bundle 加载的技能中的 `{{ var }}` → 正确替换为 config 值
10. **多平台**：CLI 和 Gateway（Telegram/Discord）均可用
