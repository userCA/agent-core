### 问题 19：Memory & Retrieval 基础子系统

- **背景**：agent-core 缺少 RAG 与长期记忆能力。需要在不改动 `agent_core/core/` 的前提下，提供可适配多种后端（mem0、Pinecone、PGVector、Chroma）的标准接口。
- **目标**：Protocol 优先 + 内存适配器验证，通过现有 Extension / Tool 桥接入运行时。

#### 19.1 关键设计

- **复用 `transform_context` hook**（`agent_core/core/loop.py:60-61`）：经典 RAG 与记忆召回均通过该 hook 注入系统消息，**核心零改动**
- **`Retriever` 与 `MemoryStore` 分离**：合并会迫使事实抽取后端（mem0）与向量搜索后端（Pinecone）采用别扭的 API；两者职责正交
- **`AgentSession.start()` 链式组合**：与现有 `before_tool_call` 相同的 monkey-patch 模式，链式聚合 Extension 的 `transform_context`，注册顺序决定包裹顺序（**后注册的更靠近模型**）
- **两阶段记忆持久化**：`MemoryExtension` 在 `MessageEnd` 入队、`TurnEnd` 刷盘，防止当前 turn 的用户消息被同 turn 的 `transform_context` 自己回声召回

#### 19.2 核心新增

- `agent_core/retrieval/base.py`：`Query` / `RetrievedChunk` Pydantic 模型 + `Retriever` Protocol
- `agent_core/retrieval/adapters/inmemory.py`：`InMemoryRetriever`（token 重叠 Jaccard 评分）
- `agent_core/retrieval/tool.py`：`RetrieverTool`，把 `Retriever` 暴露为 LLM 可调用工具（Agentic RAG）
- `agent_core/retrieval/extension.py`：`AutoRetrievalExtension`，每 turn 自动召回并注入（经典 RAG）
- `agent_core/memory/base.py`：`MemoryRecord` + `MemoryStore` Protocol（`remember` / `recall` / `forget`）
- `agent_core/memory/adapters/inmemory.py`：`InMemoryMemoryStore`，session 范围 + token 重叠排序 + 时间回退
- `agent_core/memory/extension.py`：`MemoryExtension`，两阶段持久化 + 召回注入
- `agent_core/_llm_message_utils.py`：共享 helper（`latest_user_index` / `latest_user_text`），避免在两个 Extension 中重复实现

#### 19.3 框架改动

- `agent_core/session/session.py`：`start()` 末尾新增 `_chained_transform` monkey-patch，与 `before_tool_call` 模式对称
- `docs/design.md`：新增 §10 Memory & Retrieval

#### 19.4 设计提示（已写入 design.md §10.4）

- `MemoryExtension` 当前**原样持久化用户消息**。生产环境建议外接带事实抽取的后端（如 mem0），否则连续追问会把上一轮提问本身当作"记忆"召回
- 后续真实后端（mem0 / Pinecone / PGVector / Chroma）通过 `pyproject.toml` extras 接入，不修改框架

#### 19.5 测试

- `tests/retrieval/`：base / inmemory / tool / extension 共 12 个测试
- `tests/memory/`：inmemory_store / extension 共 9 个测试
- `tests/session/test_session_transform_chain.py`：2 个测试验证 Extension transform_context 被正确串接
- `tests/test_e2e_memory_retrieval.py`：端到端场景，同时启用 RAG + 记忆，验证两类系统消息均被注入，且用户问题被持久化
- 全套件 217 PASS，无回归

### 问题 20：AIGC（NOLO 视频生成）工具与 HTTP/SSE 鉴权透传

- **背景**：scene/http_sse 需要接入咪咕 NOLO 场景视频生成 API，要求每次工具调用使用**当前 HTTP 请求**的用户 headers（uid / deviceid / channel / pacmtoken），而不是启动时静态配置
- **目标**：在框架内提供通用 AIGC 工具骨架；在 scene 层通过现有 `before_tool_call` hook + `ContextVar` 把请求 headers 透传到 `ToolContext.metadata`，**框架核心仅增 5 行**

#### 20.1 框架改动

- `agent_core/core/tool_runner.py`：`before_tool_call` 返回的 `inject_metadata` 现在会合并进 `ToolContext.metadata`，工具 `execute()` 可读取。**新增 5 行**，不破坏现有调用
- `agent_core/tools/aigc_creation.py`：通用 `AigcCreationTool` + `AigcToolConfig` + `create_nolo_video_tool()` 工厂
  - 鉴权优先级：`ctx.metadata["aigc_auth"]` > 构造参数 > 环境变量 > 默认值
  - 必填参数缺失时若提供 `hitl_schema_builder` 则抛 `RequiresHumanInput`，触发前端表单
  - 异步轮询（默认 60 次 × 3s），状态归一化（SUCCESS / FAILED / 等），URL 提取兼容多种响应嵌套
  - 失败/异常返回 `ToolResult(details={"error": ...})`，不抛出
- `tests/tools/test_aigc_creation.py`：9 个测试，覆盖鉴权优先级、HITL、payload、HTTP 成功/超时/错误、`inject_metadata` 通过 `_run_single_tool` 流到 `ToolContext.metadata`

#### 20.2 scene/http_sse 改动

- `scene/http_sse/request_context.py`：`current_request_headers: ContextVar[dict[str, str]]`，挂当前请求的 headers
- `scene/http_sse/server.py`：`/chat/stream` 入口把 `dict(request.headers)` 灌入 contextvar（FastAPI 异步上下文会自动复制到下游 task）
- `scene/http_sse/chat_assistant.py`：
  - 注册 `create_nolo_video_tool()`
  - 新增 `_auth_before_tool_call` hook：当 `tool_call.name.startswith("create_")` 时，从 contextvar 取 headers 包成 `{"inject_metadata": {"aigc_auth": {...}}}`，由 `tool_runner` 合并进 `ToolContext.metadata`
- `scene/http_sse/static/index.html`：HITL 表单 UI 适配 select 控件（模板选择）+ image_upload 控件（NOLO 需 1-3 张照片），与 `_nolo_hitl_schema` 返回的 `template_form` 对应

#### 20.3 关键设计决策

- **不**给框架核心新增"请求上下文"概念。请求上下文是 scene 层概念，通过现有 `before_tool_call` hook + Python `ContextVar` 即可解决
- **不**让工具直接读 `ContextVar`。工具仍只读 `ctx.metadata`，与具体 transport 解耦，便于在 CLI / WebSocket 等其他 scene 复用
- **`inject_metadata` 设计为合并语义**（不是覆盖），未来多个 hook 注入不同 key 不会互相覆盖

#### 20.4 已知局限

- `_auth_before_tool_call` 硬编码 `name.startswith("create_")`：未来若有非 AIGC 的 `create_*` 工具会被误注入。短期可接受，长期建议改为白名单显式列举工具名
- AIGC 真实 API 接入时需在生产环境补齐 `pacmtoken` 的鉴权续签逻辑

#### 20.5 清理

- 删除 `agent_core/tools/tasks/`：从另一个 `customer_service` 项目误粘的死代码（所有 import 都是 `from customer_service.*`），仓库内无引用，import 即崩

### 问题 21：AIGC 工具补音乐场景 + 鉴权/请求体瘦身

- **背景**：参考实际 curl 抓包，当前 `AigcCreationTool` 的 header 字段（uid/deviceid/pacmtoken）以及请求体里的 `taskSessionId`/`ext.rcToken` 经实测对服务端无影响；同时需要新增咪咕音乐（`AI_MGYY_MXG_MUSIC`）创作场景，其 `aigcInputContentList` 元素类型为 `text` 而非 `pic`
- **目标**：对齐真实 curl 的最小字段集；将 `AigcCreationTool` 泛化以支持文本输入；合并鉴权配置项以避免参数泛滥

#### 21.1 框架改动

- `agent_core/tools/aigc_creation.py`：
  - 新增 `text_content_key` 构造参数：当设置时，该 key 对应的入参会被同时写入 `aigcInputContentList` 的 `{contentType: "text", content: ...}` 元素；不影响图片入参逻辑
  - 请求体瘦身：去除所有场景的 `taskSessionId` 与 `ext.rcToken`（实测无作用），同步移除未用的 `uuid` 依赖与 `_generate_session_id` helper
  - 鉴权瘦身：headers 仅保留 `content-type` + `channel`；`pacmtoken` 改为 cookie（与 curl 一致），并以常量 `_DEFAULT_PACM_TOKEN` 兜底，待生产对接续签
  - 默认 URL 升级为 `https://`，默认 channel 调整为 `014X031`
  - 新增 `AigcAuth(channel, pacmtoken)` dataclass 合并原本散落在 `AigcToolConfig` 上的两个鉴权字段，工厂签名收敛为 `auth: AigcAuth | None`
  - 新增 `_music_hitl_schema` + `create_music_tool()` 工厂：参数 `song_name` / `lyrics` / `style` / `status`，scene=`AI_MGYY_MXG_MUSIC`，content_type=`audio`，`text_content_key="lyrics"`
  - 顺手清理 `_extract_task_id` / `_extract_status` / `_extract_result_urls` / `_extract_error` 中 basedpyright 判定不可达的 `isinstance(data, dict)` 守卫
- `tests/tools/test_aigc_creation.py`：同步 `AigcAuth` 新 API、移除已删字段（uid/deviceid/taskSessionId/ext）的断言，9 个测试全部通过

#### 21.2 关键设计决策

- **鉴权字段合并到 `AigcAuth`**：避免后续接入更多场景时构造参数继续膨胀，且语义上 channel + pacmtoken 本就是一组关联凭证
- **`text_content_key` 而非新增子类**：音乐与视频两个场景 99% 逻辑共享，仅 `aigcInputContentList` 元素类型不同；引入一个开关字段比拆出 `TextAigcTool` / `ImageAigcTool` 更简洁
- **保留按场景兜底常量**：`pacmtoken` 暂以常量内置，未来对接生产时通过 metadata 注入或 env 覆盖即可，无需再改框架
