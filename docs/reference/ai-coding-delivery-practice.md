# 复杂业务 AI Coding 交付实践：核心设计

> 来源：淘天集团-物流技术团队。面向复杂业务场景（多应用、多业务域、历史包袱重）的 AI 研发交付方法论，核心思路是**知识库分层 + 文件化 RD 流程 + 前置质量门禁**，不追求全自动化，强调人机协同。

---

## 核心哲学

```
知识库 + 工具链 → 自动化流程 → 自主协同交付
```

**工具可以换，模型可以升级，底层的团队上下文和研发协议需要自己沉淀。** 第一阶段只打底：建设知识库 + 跑通 RD 流程，不追求"端到端自动化"。

---

## 设计一：三层资产架构

```
命令协议层    .agents/commands/ + .agents/skills/    定义 /kb:* 和 /rd:* 命令的行为
知识资产层    knowledge/                              正式知识、候选知识、个人经验、模板、路由
RD 过程资产   rd/requirements/{requirementId}/        需求全生命周期产物，支持跨会话接续
```

---

## 设计二：五层知识库

解决的核心问题：知识准不准、谁确认的、需求来了先读哪部分、应用级和全局知识怎么分。

```
knowledge/
├── main/            跨应用全局知识（术语、跨应用流程、通用状态、全局约束）
├── applications/    应用级知识（每个应用独立目录）
├── candidate/       候选知识暂存区（待 review，不直接进正式库）
├── personal/        个人经验/踩坑记录（非正式，可作为入库素材）
├── template/        强约束写作模板（防止 AI 产出粒度漂移）
├── ROUTING.md       知识路由入口（最关键的文件之一）
└── INDEX.md / README.md / KNOWLEDGE-RULES.md
```

### 应用内部分层（applications/{app}/）

```
application-xxx/
├── application-xxx.md     应用总览（职责、边界、上下游）
├── INDEX.md               应用内导航（AI 先读索引，按需深入）
├── domain/
│   ├── product/           主干能力（创单、取消、状态流转等稳定流程）
│   ├── solution/          差异化扩展（某业务线对 product 的覆盖/兼容，只写差异）
│   └── base/              基础索引（API、消息、模型、Repository、字段语义）
└── tech/                  技术约束（研发规范、架构约束、异常处理、MQ 规范）
```

AI 读取路径：`应用职责 → product 主干 → solution 差异 → base 索引 → tech 规范 → 回到代码确认`

### 三条关键原则

1. **KB 提供稳定上下文，当前代码仍然是实现事实。** 接口签名、字段、枚举等易变信息，KB 只提供定位入口，改代码前必须回到仓库核对。
2. **错误知识比没有知识更危险。** AI 产出通过 candidate 暂存，经 owner 确认后才进入正式库。
3. **渐进式加载。** AI 不应该全量读取知识库，而是在正确阶段加载正确粒度的上下文。

### ROUTING：知识路由器

`ROUTING.md` 让 AI 先定位再读取，避免上下文窗口浪费：

```
需求关键词（Topic / 状态码 / 业务身份 / 接口名 / 表名）
  → ROUTING 定位候选业务域 → 候选应用 → 应用职责地图 → 知识入口 → 本地仓库路径
```

### 知识流转路径

```
personal 个人经验 → candidate 候选知识 → owner review → official 正式知识
  → 需求执行中被引用 → 代码/业务变化后更新或 deprecated
```

## 设计三：文件化 RD 流程

核心理念：**研发状态靠文件推进，不靠聊天上下文。** 产物是 Markdown/YAML，不和任何 Coding Agent 绑定。

### RD 命令流水线

```
需求/PRD/Bug
  → /rd:verify-prd           PRD 输入质量检查（fail-fast 第一关）
  → /rd:work                 路由命令，自动推断意图并引导下一步
  → /rd:clarify              需求澄清（结合知识库）
  → /rd:analyze              需求分析（知识检索 + 代码 explore）
  → /rd:decompose            拆解为 by 应用的 requirement
  → /rd:verify-requirement   编码前开发契约确认（fail-fast 第二关）
  → /rd:apply                代码实现
  → /rd:validate             requirement 与代码 diff 对账
  → /rd:code-review          发布前 CR
  → /rd:release-plan         发布/灰度/回滚计划
  → 知识回补
```

`/rd:work` 是唯一的日常入口，其余为原子能力。

### 三个关键产物

| 产物 | 作用 |
|------|------|
| **`requirement.md`** | 应用级开发契约。明确目标、非目标、影响范围、验收标准、blocked 项。跨应用需求每个应用各一份，编码会话只聚焦当前应用的契约 |
| **`implementation-check.md`** | requirement 与代码 diff 的对账结果，标记每项状态（done/partial/todo/changed/blocked） |
| **`continue-prompt.md`** | 新会话接续开发的上下文入口，解决"开发可以中断，上下文不能丢"的问题 |

### Fail-fast 设计哲学

> 能在 PRD 阶段暴露的问题，不拖到 requirement。能在 requirement 阶段暴露的问题，不拖到编码。越晚发现，返工成本越高。

## 设计四：前置质量门禁

| 门禁 | 拦截什么 |
|------|---------|
| `/rd:verify-prd` | PRD 缺口（状态码不明确、上下游未确认、Non-Goals 缺失） |
| clarify review | 阻塞问题和业务口径 |
| `/rd:verify-requirement` | 编码前开发契约完整性 |
| 方案 review | 扩展点选择、架构路径、历史兼容 |
| `/rd:validate` | requirement 与代码不一致 |
| `/rd:code-review` | 发布前代码质量与方案一致性 |

**人不重做 AI 的工作，只在高价值位置介入**：校验前置/后置、状态取值来源、历史兼容、异步调用边界、开关默认值、灰度策略等。

**不追求 100% 全 AI。** 95% 之后手改更快就手改。目标是总交付成本更低、质量更稳、风险更可控。

## 真实案例核心结论

同一个需求，两轮交付对比：

| 轮次 | 代码采纳率 | 关键差异 |
|------|-----------|---------|
| 第一轮 | ~75% | 关键架构约束（前置校验位置）未写入 requirement，AI 理解了"做什么"但搞错了"在哪做" |
| 第二轮 | 95%+ | 把"两阶段异步架构"约束明确写入 requirement + 人工补充历史兼容细节 |

**结论：AI 交付质量的瓶颈不在编码能力，在于前置阶段是否把关键业务约束表达清楚。知识库 + requirement + review 点三者协同，是质量收敛的关键。**

---

## 设计取舍总结

| 选择 | 而非 | 原因 |
|------|------|------|
| 文件化研发状态 | 工具私有状态 | 工具可换，文件可迁移 |
| 分层知识库 + ROUTING 路由 | 全量塞上下文 | 渐进式加载，避免信息淹没 |
| candidate 暂存区 | AI 产出直接入正式库 | 防止错误知识污染后续决策 |
| 前置质量门禁 | 事后返工 | 复杂业务中晚发现的问题更贵 |
| 开发者深度参与关键判断 | 全自动端到端 | 应用边界、扩展点、兼容逻辑需要人的经验 |
