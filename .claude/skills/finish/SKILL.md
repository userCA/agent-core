# 会话收尾

兜底流程。无论当前会话做了什么改动，按顺序走这三步：

---

## 检查清单

### 1. 是否有未提交变更？

```
git status --short
```

没有变更 → 直接结束。有变更 → 继续。

### 2. 更新开发日志

- 有新增/修改代码？→ 追加条目到 `docs/development-log/YYYY-MM-DD.md`（当天日期），新建文件则同时更新 `docs/development-log.md` 索引
- 修复了 bug？→ 同时检查 `docs/mistake-log.md` 是否需要追加
- 纯文案/格式/skill 文件？→ 跳过

### 3. 检查 skill 是否需要进化

**强制：逐条列出本次会话中遇到的每个 bug/踩坑/返工，逐条打分。不得跳过、不得合并、不得用"属于通用常识"理由跳过。**

输出格式（每条必须写）：

```
问题 N：[一句话描述]
  能预防吗？[是/否]
  三问：重复过？[是/否] 能说清？[是/否] 还有用？[是/否]
  → [追加到 X skill / 跳过，原因：...]
```

**"能预防吗"判断标准：** 如果下次同类问题出现，一条规则能预防吗？不依赖"是否重复过"——即使只出现一次，只要能清晰描述预防方法，就回答"是"。

**三问门槛**（来自 dev-process-optimizer）：
- 真重复过？（同一错误 ≥2 次，或 1 次但灾难性）
- 能说清怎么办？（有具体检测方法/操作步骤）
- 现在还有用？（涉及代码仍存在）

三问全部通过 → 按附录模板追加到对应 skill。任一不通过 → 跳过，但必须在"原因"中写明哪个问题不通过。

**常见错误倾向（必须反着来）：**
- "这是通用常识" → 错。常识也会忘，写进规则才可靠
- "只出现一次不算重复" → 错。灾难性的一次就够了（如数据丢失、功能完全失效）
- "太特殊了不值得" → 错。宁可多写，不要漏过
- "我已经记住了" → 错。规则是给下一次的自己和别的 agent 看的

### 4. 提交

```
git add <具体文件>
git commit -m "描述 WHY，引用开发日志问题编号"
```

---

## 注意

- 如果用户明确说"不提交"或"只是看看"，跳过提交步骤
- 不要提交 .env、credentials、secrets
- 提交前确保测试通过
